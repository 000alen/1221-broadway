# Operations model and evidence contract

This app is a decision-support model. A plausible animation is not evidence of an operational service level. Default outputs are conditional scenarios until the time inputs, demand, ordering policy and tower procedure have been measured or confirmed.

## One model, three views

The same discrete-event engine produces a representative day for map playback, repeated sampled days for uncertainty analysis, and paired scenario comparisons. No UI text declares delivery independently of engine events. A common seeded generator makes runs reproducible. Both Concord destinations have separate completion events.

## Resources and constraints

- Orders belong to a destination and are collected at all five reference pickup hubs. The per-restaurant distribution is currently unconfirmed; measured manifests should replace this assumption.
- Four reference routes are the starting plan. Additional tower loads are created if vehicle capacity requires them; queued routes wait for an available courier. A reserve is separate from active couriers.
- Pickup departure requires kitchen release, an available loading position, and completion of loading service. Queue time is generated by the resource model, not added twice to measured service time.
- Driving duration uses observed travel samples when available. Otherwise reference ranges are planning bounds sampled with an explicitly assumed triangular distribution, with a shared traffic component across a simulated day.
- Customer delivery windows apply to completed shelf delivery. Arrivals can be earlier. Order-cutoff confirmation is a separate feasibility requirement; an unknown cutoff prevents calling results calibrated.
- A selected courier callout interrupts the active route. A reserved replacement arrives after a modeled response plus transfer delay. Recovery interrupts active work but can be absorbed by a future delivery-window wait. If recovery extends past the service opening, only the excess shifts service. An absent courier waiting for a loading bay does not reserve that bay. These distributions are assumptions until local response observations are loaded. Without a replacement the affected load is unserved. Response time is an assumption unless measured for the failed route and location.
- Tower intake, runners, cart capacity and a shared elevator are explicit resources. Lobby delivery and floor delivery are different policies. Batches merge per floor until the runner actually departs, including while the request waits in a queue. New arrivals after departure require a later visit. Early staging lets placement and the return to the lobby finish before opening; shelf availability is recorded no earlier than the window start. Floor jobs return to the lobby; elevator service is not a detailed dispatch algorithm.
- An ambassador absence reduces runners until a separate local replacement arrives. A scheduled courier may assist only after completing their own deliveries. Staffing cannot be counted in two roles at once.

## Timing evidence

`data/routes.json` contains reference-generated intervals, not field observations. Those intervals must never be relabeled as measured samples. The default 7.47-minute pickup value is retained only as a reference input, not asserted to be true.

The interface does not import files or expose measurement plumbing. The engine's structured `observations` input can support future calibration: `kind`, `key`, `minutes`, `orders`, `evidence`, `source`, and `observed_at`. Supported kinds are `pickup`, `travel`, `intake`, `floor`, `elevator`, `backup`, and `handoff`. Only evidence tagged `observed` is eligible for empirical resampling; synthetic, reference and unverified inputs never count as measurements.

Pickup measures loading-start to departure, excluding queue and readiness wait. Travel measures road departure to building arrival. Floor service is per-order shelf placement, excluding elevator travel. Elevator service is a complete one-way ride, including doors and boarding. Intake and handoff are per vehicle batch. Future calibration must keep these definitions separate, retain source and timestamp, and match load size and location. Sparse samples cannot establish reliable tail behavior.

## Outputs

- Actual simulated delivery counts, unserved orders, lateness, queue time and final completion time.
- P50/P95 completion times from repeated days, alongside count of runs and a conditional on-time proportion. These quantify the configured scenario, not real-world calibration confidence.
- The main interface labels outputs as unvalidated planning estimates. A separate methodology page and downloaded report describe assumptions, missing evidence and provenance.
- Sensitivity comparisons use the same random seeds. A model cannot demonstrate causation in the real operation.

## Validation boundary

Engine tests cover conservation, resource exclusivity, windows, paired seeds, monotonic queue effects and callout recovery. Browser tests cover interaction/playback. Neither substitutes for timed route rehearsals, restaurant release confirmation, loading tests, or tower access/elevator observations.

## Generated priors

`src/priors.mjs` records every synthetic service range and its physical interpretation. A pickup consists of batch setup plus seconds per meal, plus independently modeled kitchen readiness and loading-resource queue. Elevator motion is vertical distance divided by speed, plus boarding/doors and resource waiting. Published Otis equipment speeds only bound a plausible scenario; they do not identify this building. Numerical handling priors are generated assumptions, not observations. Public delivery-platform guidance supports the decomposition but does not calibrate these kitchens.

Return routing is in `data/return-routes.json`, fetched from OSRM with full source URLs and retrieval dates. Routing times are static estimates; the added traffic bounds are explicit assumptions.

## Permanent scenario references

The model, UI, worker, route inputs, prior registry and build definition are fingerprinted together. Each released version is stored as a compressed, self-contained HTML and methodology archive in `snapshots/`, served publicly under its fingerprint. A scenario's fragment identifies this version and restores the non-default plan settings, seed, run count and playback state. This preserves calculations and the presentation of their limitations when the main app changes. Published archives must be retained.

The parser accepts only supported setting names, enumerations and bounded numeric values. It rejects duplicate keys, unknown formats, mismatched model identifiers, oversized fragments and invalid playback states. Observation data and unexposed overrides cannot be silently omitted from a share link. The archive is a reproducibility mechanism, not additional calibration evidence.

## Model 2.1 corrections

Regression coverage includes queued floor-batch consolidation, staging resource release before shelf availability, cart capacity under staging, recovery absorbed by window slack, recovery overlapping service opening, active loading/travel interruptions, loading-bay availability during absence, and comparisons at maximum staffing. Unsupported staffing additions return an unavailable comparison instead of an invented percentage or a failed analysis. Old versioned scenario links intentionally retain their archived calculations.
